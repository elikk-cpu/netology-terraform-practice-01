- `cloud_id` и `folder_id` передаются через локальный файл `personal.auto.tfvars`.
- Пример переменных находится в `src/personal.auto.tfvars_example`.
- `personal.auto.tfvars`, `terraform.tfvars`, каталоги `.terraform` и файлы состояния `*.tfstate` исключены из Git.
- Приватный ключ и файл ключа сервисного аккаунта в репозиторий не добавлялись.
- В `locals.tf` публичный SSH-ключ считывается функцией `file()` по пути `~/.ssh/id_rsa.pub`. В рабочем окружении этот путь был создан как символическая ссылка на уже существующий `~/.ssh/id_ed25519.pub`; ключи не перевыпускались.

## Выполнение заданий

### Задание 1. Группа безопасности

В `security.tf` создана группа безопасности `example_dynamic` в существующей сети `develop`.

Входящие правила сформированы динамическим блоком `dynamic "ingress"`:

| Протокол | Порт | Источник | Назначение |
|---|---:|---|---|
| TCP | 22 | `0.0.0.0/0` | SSH |
| TCP | 80 | `0.0.0.0/0` | HTTP |
| TCP | 443 | `0.0.0.0/0` | HTTPS |

Исходящие правила формируются отдельным динамическим блоком `dynamic "egress"`.

Скриншот `01-security-group-plan.png` показывает план Terraform для группы безопасности. Для полного соответствия формулировке задания сюда также нужно добавить снимок страницы группы `example_dynamic` в веб-консоли Yandex Cloud с открытыми входящими правилами.

### Задание 2. Виртуальные машины: `count` и `for_each`

**WEB-серверы — `count-vm.tf`**

Созданы две одинаковые прерываемые ВМ:

- `web-1`;
- `web-2`.

Для создания используется `count`. Обе ВМ находятся в подсети `develop`, используют общую группу безопасности `example_dynamic` и получают SSH-ключ из локальной переменной.

**Серверы баз данных — `for_each-vm.tf`**

Созданы две прерываемые ВМ через `for_each` на основе общей переменной `each_vm` типа `list(object(...))`:

| Имя | CPU | RAM, ГБ | Диск, ГБ |
|---|---:|---:|---:|
| `main` | 2 | 2 | 5 |
| `replica` | 4 | 4 | 6 |

WEB-ресурс содержит `depends_on` для `yandex_compute_instance.db`, поэтому WEB-ВМ создаются после DB-ВМ.

Публичный SSH-ключ читается в `locals.tf` функцией `file(pathexpand(...))` и передаётся в `metadata` всех создаваемых ВМ.

### Задание 3. Дополнительные диски и STORAGE-ВМ

В `disk_vm.tf` с помощью `count` созданы три одинаковых диска:

- `storage-disk-1`;
- `storage-disk-2`;
- `storage-disk-3`.

Размер каждого диска — 1 ГБ, тип — `network-hdd`.

Также создана одна ВМ `storage`. Дополнительные диски подключаются к ней динамическим блоком `dynamic "secondary_disk"` с `for_each`. Для ВМ используется отдельная подсеть `develop-storage`.

### Задание 4. Динамический Ansible Inventory

В `ansible.tf` используется ресурс `local_file`, а содержимое inventory формируется функцией `templatefile()` из шаблона `hosts.tftpl`.

Шаблон содержит три группы:

- `[webservers]` — WEB-ВМ;
- `[databases]` — DB-ВМ;
- `[storage]` — STORAGE-ВМ.

Для каждой машины циклом выводятся имя, внешний IP-адрес (`ansible_host`) и внутреннее полное доменное имя (`fqdn`). В шаблоне нет вручную заданного количества машин: состав групп передаётся из ресурсов Terraform.

Сгенерированный файл находится в `src/hosts.ini`.

Ansible Inventory успешно создан и проверен: в нём присутствуют все пять ВМ, распределённые по трём группам, с `ansible_host` и `fqdn`.

## Проверка и запуск

Для повторного запуска в рабочем окружении нужно создать локальный `personal.auto.tfvars` со своими `cloud_id` и `folder_id`, а также обеспечить доступность файла сервисного аккаунта и публичного SSH-ключа.

```bash
terraform init
terraform fmt -check
terraform validate
terraform plan
terraform apply

terraform state list
cat hosts.ini
```

После сохранения скриншотов и отправки кода в Git необходимо удалить созданные этим проектом ресурсы:

```bash
terraform destroy
```

Существующая сеть `develop` и существующие WEB/DB-подсети подключаются через `data`-источники и этим проектом не создаются.
